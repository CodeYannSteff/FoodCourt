# Muncho — Food Court Mobile Ordering (Glovo × Uber Eats)

A unified, high-performance food ordering web app optimized for mobile devices. 100% static —
host it on any FTP server or GitHub Pages. Real Google Pay sheet (TEST mode), Apple Pay ready,
and zero-backend order dispatch to the restaurant (ntfy push + webhook + WhatsApp ticket).

Powered by **teen minds** · Argeș Mall · Pizzeria Sapori Italia live menu.

---

## 📱 Features

- **Glovo-Inspired Top Header**:
  - Store location selector with address pill (`Argeș Mall · Food Court, Nivel 1`).
  - Order mode toggle: `Ridicare` (Pickup) and `Livrare` (Delivery).
  - Instant live search bar with clear button (`✕`).
  - Circular category bubbles rail with high-res food imagery.
- **Uber Eats-Inspired Feed & Store Pages**:
  - Hero promotional carousel with snap scrolling and indicator dots.
  - Dish cards featuring title, description, ratings (`★ 4.8`), prep time, price, and intuitive `+` add / stepper buttons.
  - "Top Picks: Pizza" horizontal swipe rail.
  - Sticky category pills bar on merchant page (`venue.html`) for quick section jumping.
- **Mobile-First UX**:
  - 48px+ touch targets, iOS safe area inset support (`env(safe-area-inset-top)`, `env(safe-area-inset-bottom)`).
  - Floating pill-shaped cart tray that slides up when items are added.
  - Smooth bottom sheets for Cart, Venue info, and Orders history.
  - Fixed mobile bottom navigation bar (`Acasă`, `Caută`, `Meniu`, `Comenzi`, `Coș`).
- **Ordering without accounts or forms**: no name/phone typing — the order is
  identified by its pickup code. No "Comenzi" tab; the flow is menu → cart →
  save → show code at the register.
- **Payments (100% static, no backend)**:
  - **Salvează Comanda / Plată la tejghea (main flow):** the order is saved and
    the customer gets a pickup code + QR ticket. The cashier scans the code —
    `comanda.html` opens the order summary — and takes payment at the register.
  - **Google Pay**: official Google Pay button in TEST mode — opens the Google
    Pay sheet on secure origins (GitHub Pages / localhost), returns a test
    token stored as the payment reference.
  - **Apple Pay**: button appears only with a configured Merchant ID; the real
    sheet additionally needs a verified HTTPS domain (see below).
- **Order dispatch to the restaurant (zero-backend)**:
  - Instant push to the counter via ntfy (the kitchen opens the topic URL and
    every order pops up live), optional webhook POST of the order JSON to the
    restaurant's real order system, plus the existing WhatsApp ticket button.
- **Order Tracking & Digital Receipt**:
  - Animated order code `#M-###`.
  - Live 3-step progress timeline: `Comandă primită` → `În pregătire` → `Gata de ridicare`.
  - Order history saved to `localStorage` under `fc-orders`.

## 🌍 Hosting: FTP or GitHub Pages (pure static)

No build step, no server, no Node.js at runtime. Just upload the files.

### GitHub Pages (free HTTPS — needed for the Google Pay sheet)
1. Create a repo (e.g. `muncho-foodcourt`) and push this folder's contents to the
   repo **root** (so `index.html` is at the top level).
2. GitHub → repo **Settings → Pages** → *Deploy from a branch* → branch `main`, folder `/ (root)` → Save.
3. Your site is live at `https://<user>.github.io/muncho-foodcourt/` in ~1 minute.
4. Open `checkout.html` on your phone (Chrome/Android) → the real **Google Pay**
   button appears; tapping it opens the genuine Google Pay sheet (TEST mode).

### Any FTP / cPanel hosting
Upload everything inside `FoodCourt/` to `public_html/` (FileZilla / WinSCP /
cPanel File Manager). Done — open your domain over **HTTPS**.

> Plain `http://` LAN hosting (e.g. `./serve-foodcourt.sh`) still works for
> browsing and saving orders — the wallet buttons stay visible but explain
> they need HTTPS for their sheets (Google's rule, not ours).

## 💳 Payments + order API (all settings in `js/config.js`)

### Why there is no "real processor without backend" (straight answer)
Card processors (Stripe, Netopia, PayU, Revolut…) require a server: secret keys
must never ship in frontend JS and amounts must be validated server-side, or
anyone could pay 0.01 lei for anything. PayPal can't help either — RON isn't a
PayPal currency and its current SDK also calls a server. Apple Pay additionally
demands server-side merchant validation. So on a purely static host (FTP /
GitHub Pages) the save-for-register flow is the correct architecture, and the
site is built for it — the finalized order (with payment reference) is what
flows to the restaurant's system.

### Google Pay (works today, pure static)
Nothing to configure. On any HTTPS page the checkout shows the Google Pay
button — the section **never disappears**: where supported you get Google's
official button opening the sheet (TEST mode, test token stored as reference);
everywhere else a branded `G Pay` button stays visible and explains what's
needed (HTTPS + Chrome/Android) when tapped.

### Apple Pay (one-time live setup — Apple's rules, not ours)
Apple opens its sheet only after **server-side merchant validation**. The
checkout shows the  Pay button only when `applePayMerchantIdentifier` is set,
and the sheet itself additionally needs a verified HTTPS domain:
1. Enroll in the Apple Developer Program and create a Merchant ID
   (e.g. `merchant.ro.muncho.foodcourt`) → put it in
   `applePayMerchantIdentifier` in `js/config.js`.
2. Serve Apple's domain-verification file at
   `/.well-known/apple-developer-merchantid-domain-association` on your HTTPS
   domain (on GitHub Pages: commit the file at that path).
3. Add a tiny merchant-validation endpoint (any serverless function) that signs
   Apple's validation URL with your merchant certificate.
The `ApplePaySession` code path in `js/payment.js` is already written for this.

### Where orders go — the order API (`dispatch` in `js/config.js`)
1. **ntfy push (default on):** every finalized order is POSTed to
   `https://ntfy.sh/<ntfyTopic>`. The counter installs the free ntfy app
   (Android/iOS) or opens the topic URL — orders pop up live with sound.
   Change `ntfyTopic` to something private before real use.
2. **Order webhook = your API (optional):** set `orderWebhookUrl` to POST the
   full order JSON to the restaurant's real order/billing system — no UI
   changes needed. Payload shape:
   ```json
   {
     "source": "muncho-foodcourt",
     "order": {
       "id": "ord_…", "code": "M-123", "total": 45.5,
       "payMethod": "TEJ | GOOGLE PAY | APPLE PAY …",
       "payTx": "tej_… / gpay_test_… (payment reference)",
       "items": [{ "title": "Pizza", "qty": 2, "price": 32.0 }],
       "customer": { "name": "", "phone": "", "notes": "" },
       "saporiCartId": "…"
     }
   }
   ```
   Later, when a backend/processor exists, point this URL at it and real
   charging plugs in behind the same contract.
3. **WhatsApp ticket:** the success screen keeps the "Trimite tichet WhatsApp"
   button (prefilled kitchen ticket to the counter's number).

## 🔄 Menu Catalog Sync

To update products and prices from the partner restaurant API:

```bash
node tools/sync-menu.js
```

You can set up a cron job on your server (or run locally and FTP upload `js/menu.generated.js` and `assets/img/`):
```bash
0 */6 * * * cd /path/to/FoodCourt && node tools/sync-menu.js >> sync.log 2>&1
```
